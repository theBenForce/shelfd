# Per-Paragraph 256-Dimension Vector Embeddings & SQLite FTS5 Retrieval

* Status: accepted
* Deciders: Lead Systems Architect, @core, @librarian, @mcp, @reader
* Date: 2026-09-08

## Context and Problem Statement

Previously, Shelfd used chapter-level summaries generated by an autoregressive LLM (`llama3.2:3b`) and embedded into `sqlite-vec` at 1536 dimensions (ADR-0005). 

While chapter summaries kept the vector count low (~20 vectors per book), running a 3B parameter model to summarize 20–30 chapters per book incurred severe ingestion latency: **5 to 20 minutes per book** on typical homelab/NAS CPU hardware. Furthermore, search results returned entire chapter summaries rather than specific passages, inflating context window token usage for MCP AI agents and the in-book RAG chat (ADR-0013).

How should text chunking, storage, and retrieval be structured to eliminate the generative ingestion bottleneck, enable instant search upon upload, and deliver token-efficient passage excerpts?

## Decision Drivers

* **Instant Ingestion**: Uploaded books must be searchable in milliseconds without waiting for a chat LLM queue.
* **Token Economy for Agents & RAG**: Search hits should provide compact paragraph excerpts (< 100 tokens) so models do not exhaust context budgets.
* **Low Storage Footprint**: Keep vector storage within Shelfd's homelab philosophy (< 50MB for ~100 books) inside `/data/sqlite.db`.
* **Single-File ACID Integrity**: Maintain atomic cascades and single-file backup ergonomics in SQLite without adding a secondary vector database.

## Considered Options

* **Per-Paragraph 256d Vector Embeddings + SQLite FTS5 (Chosen)**
* **Full-Text Chunking with Secondary Columnar Vector Store (LanceDB)**
* **Keep Chapter Summaries + Add FTS5 Only**

## Decision Outcome

Chosen option: **Per-Paragraph 256d Vector Embeddings + SQLite FTS5**.

1. **Dual Ingestion Strategy**:
   * **Synchronous Lexical Layer**: On EPUB ingestion, text is extracted, chunked into consolidated paragraphs (~150–250 tokens / 600–1200 characters), and indexed into an SQLite `fts5` virtual table (`paragraphs_fts`) via database triggers in < 50ms.
   * **Asynchronous Semantic Layer**: The background worker embeds paragraphs directly using a fast encoder model (`nomic-embed-text` or `text-embedding-3-small`) truncated to **256 dimensions** via Matryoshka Representation Learning (MRL).
2. **256 Dimensions & MRL**:
   * Slicing embeddings to 256 dimensions with L2 normalization yields **67% storage reduction** (~51 MB for 50,000 paragraphs / ~100 books) with only a ~2.0% variance on MTEB retrieval benchmarks.
   * Flat KNN scans in `sqlite-vec` execute in ~10–20ms using SIMD.
3. **Retrieval Ergonomics**:
   * MCP `search_library` and In-Book RAG Chat (`POST /api/v1/books/{id}/chat`) return exact paragraph excerpts with book, chapter, and paragraph span citations (`Paragraphs 14–16`).
   * When broader context is needed, models expand the reading window via `read_chapter_content`.

## Consequences

### Positive Consequences
* **Ingestion Speedup**: Eliminates 5–20 minute generative LLM summarization. Ingestion is instant for FTS5 and takes ~3–8 seconds for vector embedding.
* **Exact Passage Grounding**: In-book RAG chat and MCP agents cite exact quotes and paragraphs rather than vague high-level synopses.
* **Zero Dependency on Large LLMs for Indexing**: Works with lightweight embedding models on low-power NAS hardware.
* **Single-File Simplicity**: All relational tables, FTS5 indexes, and `vec_paragraphs` tables live inside `/data/sqlite.db` with cascading deletions.

### Negative Consequences
* **Higher Vector Row Count**: ~50,000 rows per 100 books in `paragraphs` vs ~2,500 in `chapters`. Managed by reducing dimensions to 256d.
* **Benchmark Variance**: ~2.0% lower MTEB average score compared to full 768d, though imperceptible for personal library retrieval.
